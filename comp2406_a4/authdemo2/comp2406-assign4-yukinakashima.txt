4.
authdemo2 does not allow users to upload invalid submissions. Furthermore, such invalid submission will not be 
stored in the server's database. The reason for this being that the checkSubmission() function in validator-core.js 
is used in the server-side in authdemo2.js before the database insertion call function, as shown below.

    const q = checkSubmission(submission.filename, submission.filecontents);

    if (!q) {
        return {
            contentType: "text/plain",
            status: status_BAD_REQUEST,
            contents: "Bad Request: Invalid parsed submission upload",
        };
    }
        
    let result = db.addSubmission(q);

Due to the design of checkSubmission(), the function returns null if at any point the submission is invalid, where 
then the if statement detects that and returns a Bad Request response instead of letting the database insertion 
function to be called. 

I verified this by commenting out every `return;` in checkSubmission() in validator-core.js so that even if the 
submission is invalid, the file is parsed and sent to the addSubmission function in authdemo2.js. After selecting a file, 
getting an error on the tag saying wrong number of questions, and pressing upload, I was able to check the 
submission in the database later by logging in as an admin. This proved that the return value of checkSubmission() 
stopping invalid submissions to be uploaded to the server.

7.
authdemo2 stores an individual sessionid in a cookie, to indicate that a user logged in instead of a username. 
This solution has many advantages comprised mainly in security, scalability, and maintainability. Since session IDs 
can be random tokens, they minimize the value of stolen cookies, compared to username cookies that can expose personal 
or identifying information. Furthermore, by having the session IDs stored in server-side data, sessions can be terminated 
or invalidated by the server side, regardless of client-side cookies. This security feature comes along with advantages 
in scalability thanks to centralized session data storage management and the client maintaining complete statelessness, 
as the server handles most of the logic.

However, those same advantages come with same disadvantages, at scale, the management of high volume sessions can become 
expensive quickly. Also, the concept of managing states of clients on the server side goes against the stateless design 
principles. This uses unecessary resources on the server-side and overall increases latency from the session ID validation 
and increased fetch() requests.
